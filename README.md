# 名刺管理アプリ

営業担当者が受け取った名刺の画像をAIで読み取り、確認・修正してから登録し、後で氏名・会社名で探せるWebアプリです。1組織で使うシングルテナント構成で、PCのブラウザーでの利用を想定しています。

利用の流れは、名刺画像の取り込み、AIによる読み取り、利用者による確認・修正、登録、検索・連絡先の確認です。AIの読み取り結果は、利用者が画像と見比べて「登録」を押すまで保存しません。

## 1. 環境の立ち上げ

### 前提環境

- Python 3.9以上（macOS 26.6 の Python 3.9.6 で確認しました）
- 採用担当者から提供されたLLMのAPIキー（Claude・GPT・Geminiのどれでも動きます）

### 依存関係の導入

```bash
git clone <このリポジトリのURL>
cd <リポジトリのフォルダ>
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

### 環境変数

値はリポジトリに含めていません。起動する人がシェルで設定します。

| 変数 | 必須 | 意味 |
|---|---|---|
| `LLM_API_KEY` | 必須 | 採用担当者から提供されたAPIキー。サーバー側だけで使い、ブラウザーには送りません |
| `ADMIN_EMAIL` | 初回のみ | 初期adminのメールアドレス。データベースにadminがいないときだけ使います |
| `ADMIN_PASSWORD` | 初回のみ | 初期adminのパスワード（8文字以上） |
| `LLM_PROVIDER` | 任意 | `anthropic`・`openai`・`gemini` のどれか。空ならキーの先頭（`sk-ant-`、`sk-`、`AIza`）から判定します |
| `LLM_MODEL` | 任意 | 使うモデル。空なら `claude-opus-5-5`・`gpt-5.4-mini`・`gemini-2.5-flash` を使います |
| `DATA_DIR` | 任意 | データの保存先。既定は `./data` |
| `SECRET_KEY` | 任意 | セッションの署名鍵。空なら初回に `data/secret_key` を作って使い続けます |
| `PORT` | 任意 | 待ち受けのポート。既定は 8000 |

### 起動

`start.sh` は、未設定の値をその場で聞きます。キーとパスワードは画面に表示されず、ファイルにも残りません。

```bash
PYTHON=.venv/bin/python bash start.sh
```

環境変数を先に設定しておけば、何も聞かれずに起動します。

```bash
export LLM_API_KEY=...        # 提供されたキー
export ADMIN_EMAIL=you@example.com
export ADMIN_PASSWORD=...     # 8文字以上
.venv/bin/python -m flask --app app run --port 8000
```

ブラウザーで http://127.0.0.1:8000 を開きます。macOSではポート5000をAirPlayが使うことがあるため、既定を8000にしています。

## 2. 使用技術・AIモデル・対応画像形式

| 区分 | 内容 |
|---|---|
| 言語・フレームワーク | Python、Flask、Jinja2（サーバー側でHTMLを組み立てます） |
| 保存 | SQLite（`data/app.db`）と画像ファイル（`data/images/`） |
| 画像の検査・縮小 | Pillow |
| LLMの呼び出し | Claudeは公式SDK（anthropic）、GPTとGeminiはhttpxでREST APIを直接呼びます |
| 既定のモデル | Claude `claude-opus-5-5`、GPT `gpt-5.4-mini`（提供キーで4モデルを比べて選定。5章を参照）、Gemini `gemini-2.5-flash` |
| 対応画像形式 | JPEG・PNG・WebPはそのまま保存します。GIF・BMP・TIFFも受け付け、PNGに変換して保存します（アニメーションGIFや複数ページのTIFFは1枚目）。1枚5MBまで。HEICは、`pillow-heif` を入れた環境では受け付け、入れていない環境ではJPEGに書き出してから取り込むよう案内します |

画像の形式は拡張子ではなく中身で判定し、対応しない形式は取り込み画面で理由を表示して断ります。TIFFはブラウザーで表示できないことが多いため、変換して保存します。

## 3. 利用者と閲覧権限

### 初期adminの設定

初回の起動時に `ADMIN_EMAIL` と `ADMIN_PASSWORD` からadminを1人作ります。adminが1人でもいれば、2回目以降の起動ではこの2つを使いません。

### 利用者の追加

1. adminでログインし、上部の「利用者と閲覧許可」を開きます。
2. メールアドレスを入れて「追加」を押します。初期パスワードの欄を空けておくと、システムが12文字のパスワードを発行し、その画面に一度だけ表示します。指定したいときは8文字以上で入力します。role は user で作ります。
3. 初期パスワードを本人に直接伝えます。招待メールは送りません（課題で任意とされているため）。
4. 本人は初回のログインでパスワードの変更画面に送られ、自分だけが知るパスワードに変えるまで他の画面を使えません。このため、adminが初期パスワードの控えを持ち続ける必要はありません。
5. 本人がパスワードを忘れたときは、adminが利用者一覧の「パスワードを再発行」を押します。新しいパスワードが一度だけ表示され、本人は次のログインで再び変更します。

### 確認用アカウントの使い方

評価する方の手元ではデータベースが空から始まるため、次の手順で確認用の利用者を作ります。

1. 初期adminでログインし、上の手順で一般利用者を2人追加します（例 `user1@example.com`、`user2@example.com`）。表示された初期パスワードを控えます。
2. 別のブラウザー（またはシークレットウィンドウ）で user1 としてログインし、パスワードを変更してから名刺を登録します。
3. user2 でログインすると、user1 の名刺は一覧に出ず、詳細や画像のURLを直接開いても「Not Found」になります。
4. adminが user2 に企業・部署・人物の許可を付けると、その範囲だけが user2 に見えるようになります。

### role と閲覧許可

- role は users テーブルの `role` 列（`admin` か `user`）で持ちます。画面から role を変える機能はありません。
- adminは、登録者に関係なくすべての名刺を閲覧できます。
- userは、自分が登録した名刺と、adminが許可した範囲の名刺を閲覧できます。どれか1つを満たせば閲覧できます。
- adminは「利用者と閲覧許可」で利用者ごとに「確認・変更」を開き、許可の確認・付与・解除を行います。同じ画面に、その利用者が今閲覧できる名刺の一覧も出します。

| 許可の単位 | 選び方 | 判定 |
|---|---|---|
| 企業 | 登録済みの会社名から選ぶ | 会社名が一致する名刺 |
| 部署 | 登録済みの「会社名と部署名の組」から選ぶ | 会社名と部署名の両方が一致する名刺 |
| 人物 | 登録済みの名刺から1枚選ぶ | その名刺だけ |

## 4. 設計上の判断と仮定

| 判断 | 理由 |
|---|---|
| 権限の判定を1か所（`access.py`）にまとめ、一覧・検索・詳細・画像のすべてがそこを通る | 画面ごとに判定を書くと、どれか1つで漏れるため。権限が無い名刺も存在しない名刺も、同じ404を返します |
| 部署の許可は「会社＋部署」の組で持つ | 別会社の同名部署（例 どちらも「営業部」）に許可が広がらないようにするため |
| 人物の許可は名刺1枚（名刺ID）で持つ | 同姓同名の別人に広がらないようにするため。同じ人の新しい名刺を登録したときは、許可を付け直す必要があります |
| 会社名・部署名の照合は、全角半角・空白の数・英字の大小だけをそろえる | 「ＡＢＣ商事」と「ABC商事」は同じと見なします。「ABC商事」と「ABC商事株式会社」は別と見なします。あいまいに一致させると、意図しない会社に許可が広がるためです |
| 許可の対象は、自由入力でなく登録済みの名刺から選ぶ | 打ち間違いで、誰にも当たらない許可を作らないため |
| 登録者は、ログイン中の利用者をサーバー側で記録する | フォームの値を使わないので、登録者を偽れません。role もリクエストのたびにデータベースから読みます |
| AIの読み取り結果は保存せず、確認画面で「登録」を押したときだけ保存する | AIの誤りを人が直してから残すため |
| LLMには文字の書き起こしだけを任せ、形式の確認はPythonで行う | メールアドレス・電話番号・URLの形式と氏名の有無を、コードで確かめて画面に注意を出します |
| 名刺に無い項目は空欄にするよう指示し、推測での補完を禁じる | 課題の要件のため。AIが読み取りに自信の無い項目は、確認画面で色を付けます |
| 名刺に書かれた文はデータとして扱い、そこにある指示には従わないようLLMに指示する | 画像の中の文で動作を変えられないようにするため |
| LLMに送る画像は長辺1568pxに縮める（保存するのは元の画像） | 大きな写真ほどトークンが増えるため |
| 読み取りに失敗しても、取り込んだ画像は残し、再読み取りか手入力で登録できる | 課題の「失敗時の案内」のため |
| フォームの送信にはCSRFトークンを付ける | 別のサイトから、ログイン中の利用者に許可の付与などを送らせないため |
| パスワードは pbkdf2-sha256 でハッシュ化する | macOS標準のPython 3.9では scrypt が使えないため |
| 初期パスワードは自動で発行して一度だけ表示し、初回ログインで本人に変えさせる | adminが利用者ごとにパスワードを考えたり、控えを保管したりしなくて済むようにするため |
| データは同じPCのSQLiteファイルと画像フォルダに置く | ブラウザーやアプリを閉じても残り、評価者が追加の契約や設定無しに起動できるため。クラウドの同期フォルダにSQLiteを置くと、同期の途中でファイルが壊れることがあるので避けました |

## 5. 動作確認

### 自動テスト（pytest）

LLMは差し替え、ネットワーク無しで動きます。

```bash
.venv/bin/python -m pytest -q tests
```

結果：**45 passed**（2026-11-10、macOS・Python 3.9.6）。確かめている内容は次のとおりです。

| 区分 | 確かめていること |
|---|---|
| ログイン | 初期adminがログインできる。未登録のメールアドレスではログインできない。ログアウト後は一覧を開けない |
| 初期パスワード | 空欄なら12文字を発行して一度だけ表示する。発行されたパスワードでログインすると、変更するまで他の画面に進めない。再発行すると再び変更を求める |
| 閲覧権限 | 許可の無いuserは自分の名刺だけを見る。adminはすべてを見る |
| 閲覧権限 | 別会社の同名部署、同姓同名の別の名刺、会社名が空の名刺には許可が広がらない |
| 閲覧権限 | 許可を1つ解除しても、別の許可や登録者としての権限が残れば見える。利用者を識別できなければ何も見えない |
| 直接のURL | 他人の名刺の詳細・画像・検索結果・取り込み途中の画像を、URLを直接指定しても取得できない |
| admin専用 | userは利用者の追加と許可の付与ができず、自分に許可を付けられない |
| 登録 | 読み取り結果は登録前に保存されない。修正した値で保存され、登録者はログイン中の利用者になる。フォームで登録者を偽っても無視される |
| 失敗時 | キーが無いなど読み取りに失敗しても、手入力で登録できる。氏名が空なら登録できない。画像でないファイルは断る |
| 画像の形式 | GIF・BMP・TIFFを受け付けてPNGに変換し、画像として配信できる |
| 永続化 | アプリを作り直しても（再起動に相当）、名刺と利用者が残る |
| AIの出力 | 項目の欠け・文字列でない値・不正な項目名を空欄にそろえ、注意を出す。キーの先頭から会社を判定する |
| LLMの呼び出し | GPTとGeminiは、HTTPの応答を疑似のものに差し替えて、送る内容（認証ヘッダー、画像、項目の指定）と応答の読み取りを確かめる。401・429・503を、原因の分かる案内文に変える。大きな写真は長辺1568pxに縮めて送る |

### 名刺画像での読み取り確認

名刺画像ごとに、画像を見て期待する8項目を `<画像名>.expected.json` に書き、`eval_cards.py` で読み取り結果と比べます。項目ごとに一致を判定し、違った項目と1枚あたりのトークンを表示します。画像と期待値には個人情報が含まれるため、リポジトリの外（`.gitignore` 済みの `local_check/`）に置いています。

```bash
LLM_API_KEY=... .venv/bin/python eval_cards.py local_check
```

用意した確認用の画像は次のとおりです。

| 画像 | 内容 | 見ること |
|---|---|---|
| 架空の名刺1（日本語） | 8項目すべてを記載。部署と役職を別の行に記載 | 8項目の書き起こし、部署と役職の分け方 |
| 架空の名刺2（英語） | 住所とWebサイトを書いていない。隅に「AIへの指示」を装った一文を入れた | 無い項目を推測で埋めず空欄にするか。名刺の中の指示に従わないか |
| Web上の名刺の見本・写真6枚 | 見本集から切り出した名刺、机に並べて撮った名刺の写真、手で持って撮り指で一部が隠れた写真など | 実際の写真での読み取り。隠れた項目を推測で埋めないか |

結果：最初に提供されたキーは、OpenAIのAPIが `HTTP 401 Incorrect API key provided` を返して使えませんでした（モデル一覧の取得でも同じ）。課題3章に従い採用担当者へ連絡し、新しいキーを受け取りました。新しいキーでは、モデル一覧の取得がHTTP 200になり、86個のモデルが使えました。

架空の名刺4枚を、提供キーで使える4つのモデルで読み取り、既定のモデルを決めました（2026-11-10 14:00ごろ）。

| モデル | 一致した項目 | 1枚あたりの時間 | 1枚あたりのトークン（入力／出力） |
|---|---|---|---|
| `gpt-5` | 16/16（2枚で打ち切り） | 約13秒 | 1,385／約1,050 |
| `gpt-5.4` | 32/32 | 1.5〜1.9秒 | 約2,240〜2,530／66〜106 |
| `gpt-5.4-mini`（既定に採用） | 32/32 | 1.5〜2.5秒 | 約2,240〜2,530／66〜106 |
| `gpt-4.1-mini` | 32/32 | 1.3〜1.7秒 | 約2,780〜3,180／54〜121 |

`gpt-5` は答える前の推論で出力が約1,000トークン増え、1枚13秒かかりました。架空の名刺4枚では正答数に差が無かったため、速さと費用の釣り合いから `gpt-5.4-mini` を既定にしました。どのモデルも、英語の名刺で住所とWebサイトを空欄のまま残し、名刺の中の「AIへの指示」に従いませんでした。`LLM_MODEL` で変えられます。

続けて、既定の `gpt-5.4-mini` で10枚を読み取りました（2026-11-10 14:09）。名刺に無い項目と、名刺だけでは決められない項目（表と裏で会社名が違うなど）は採点から外しています。電話番号は、TELや「電話」などの見出しを除いた数字で比べています。

| 画像 | 一致 | 違った項目と内容 |
|---|---|---|
| 架空の名刺4枚（日本語、英語、写真風、電話2つ） | 32/32 | なし |
| 見本の名刺（ドイツ語、表と裏が1枚に写る） | 3/3 | なし |
| 中国語の名刺 | 6/7 | 部署（香港工作小組）を空欄にした |
| 行政書士の名刺の見本 | 7/8 | 住所の町名を1字違えた（大成町を大蔵町）。期待値は小さな画像から目で読んだため、期待値の側の誤りもありえます |
| 手で持って撮り、氏名・電話・メールが指で隠れた写真 | 6/7 | 電話番号の見える先頭3桁（017）を書き出した。ただし「読み取りに自信が無い項目」として電話番号に印を付けたので、確認画面では色付きで表示されます。氏名とメールは推測で埋めずに空欄にした |
| 机に並べた名刺を斜めに撮った写真（黒い紙、白い文字、幅約340px） | 3/6 | 役職を空欄にした。メールアドレスと住所の一部を別の文字に読み違えた |
| 同じ写真の別の名刺（紺の紙、幅約280px） | 4/6 | 氏名を読み違えた（浅田未来を没田未菜）。電話番号の1つに郵便番号を混ぜた |

合計69項目中61項目（88%）が一致しました。1枚あたり1.4〜2.0秒、入力約580〜2,650トークン、出力約45〜110トークンです。印刷データの名刺はほぼ正確に読めました。一方で、解像度の低い写真では氏名やメールアドレスを読み違えることがあります。このため、確認画面で画像と見比べてから登録する流れを必須にしています。写真の読み取りを上げる次の手は、取り込み時に一定以上の解像度を求めることと、自信の無い項目が多い名刺だけを上位のモデルで読み直すことです。

キーが無効なときは、取り込み後の確認画面に「APIキーが受け付けられませんでした（HTTP 401）」と出ます。画像は保存したまま残るので、手で入力して登録するか、キーを直した後に「AIでもう一度読み取る」を押せます。この流れはテストで確かめています。

初期adminでログインし、次の画面が表示されることを確かめました（2026-11-10、Chrome系ブラウザー）。

| 手順 | 結果 |

| 初期adminでログイン | 名刺一覧が表示される |

未登録のメールアドレスで断られることは、自動テストで確かめています。画像を選んだときのプレビューと、読み取り中にボタンを押せなくする動きは、ブラウザーでは試していません。実際のLLMを使った「取り込みから登録まで」の通しの確認は、未記入（実施後に記入）です。

## 任意機能（課題6章）の対応

| 任意の項目 | 対応 |
|---|---|
| スマートフォンへの最適化 | 画面幅640px未満で、表を横スクロールにし、ボタンを押しやすい大きさにしました。実機では未確認です |
| すべての画像形式への対応 | JPEG・PNG・WebPはそのまま、GIF・BMP・TIFF・HEIC（`pillow-heif` を使用）はPNGに変換して保存します |
| 大量の名刺の処理 | 「まとめて取り込む」で最大20枚を一度に取り込み、AIで読み取ります。登録は1枚ずつ確認してから行います。取り込み途中の一覧から、後で確認を再開できます |
| パスワード再設定 | ログイン画面の「パスワードを忘れた場合」から、再設定用のリンクをメールで受け取れます。リンクは30分有効で、1回だけ使えます。登録の有無が分からないよう、同じ案内を返します。管理者による再発行もできます |
| 招待メールの送信 | 管理者が利用者を追加すると、ログイン先と初期パスワードを書いた招待メールを送ります。`SMTP_HOST` などを設定するとSMTPで送り、未設定のときは `data/outbox/` にメールの内容を保存します |
| 利用者による新規登録、複数組織の管理 | 作っていません。課題が「1組織のシングルテナント」「利用者はadminが追加する」と定めており、閲覧権限の前提とぶつかるためです |
| 本番インフラへのデプロイ、外部IdP・SSO | 作っていません |

ほかに、課題の基本機能を補うものとして、次を足しました。

- 登録後の名刺の編集。登録者と管理者だけが直せます。許可で閲覧している利用者は読むだけです。
- 名刺の詳細で、管理者が「この名刺を閲覧できる一般利用者」と理由（登録者、企業の許可など）を確かめ、その場で人物の許可を付けられる欄。
- 「使い方」の画面。ログイン前でも読めます。

メールの送信に使う環境変数（任意）：`SMTP_HOST`、`SMTP_PORT`（既定587）、`SMTP_USER`、`SMTP_PASSWORD`、`MAIL_FROM`。実際のSMTPサーバーでの送信は試していません。

## 6. 制約・未実装・未確認

- パスワードの再設定、利用者の削除・無効化、名刺の編集・削除は作っていません。
- 人物の許可は名刺1枚単位です。同じ人の名刺が2枚あれば、許可は別々に付けます。
- 画像は1枚ずつ取り込みます。名刺の裏面は別の名刺として扱います。
- 画面幅640px未満では、表を横にスクロールさせ、ボタンを押しやすい大きさにしています。実際のスマートフォンでは試していません。
- 開発用のサーバー（Flaskの組み込みサーバー）で動かしています。本番での配置は課題で任意のため、行っていません。
- 提供された名刺画像は受け取っていないため、架空の名刺と、Web上の名刺の見本・写真で確認しました（5章を参照）。ClaudeとGeminiの呼び出しは、実際のキーでは試していません。
- カメラで撮影して取り込む機能はありません。課題がPCのブラウザーでの利用を想定しているため、画像ファイルを選ぶ形にしました。
